## ⚠️ ช่องว่าง Compliance / PDPA — ทั้ง 4 ฟิลด์ต้องทดแทน

| สิ่งที่ต้องการ | ฟิลด์ที่ใช้แทน | ตาราง | ปัญหา |
|---|---|---|---|
| วันที่ให้ consent | `CreateDate` | `PDPA` | คือวันสร้างเรคอร์ด **ไม่ใช่**วันที่ลูกค้ากดยินยอมจริง |
| ช่องทางที่ยินยอมให้ติดต่อ | `CreateByEmail` | `PDPA` | คืออีเมลผู้บันทึก **ไม่ใช่**ช่องทางที่ลูกค้าเลือก |
| สถานะการถอนความยินยอม | `PDPAPersonal` | `PDPA` | เป็นสถานะปัจจุบัน ไม่มีประวัติการถอน |
| การยินยอมการตลาด | `PDPAPromotion` | `PDPA` | ใช้ได้ใกล้เคียงที่สุดใน 4 ตัว |

**นี่คือความเสี่ยงทางกฎหมาย ไม่ใช่แค่ช่องว่างข้อมูล**
PDPA ต้องพิสูจน์ได้ว่า *ใคร ยินยอมอะไร เมื่อไหร่ ผ่านช่องทางไหน และถอนเมื่อไหร่* — K2 ตอบได้ไม่ครบสักข้อ

### ทางออกที่เสนอ

**ให้ CRM เป็น system of record ของ consent** เพราะ `customer_master` มี `consent_personal` / `consent_product` / `consent_promotion` แยกชัด และ `members.pdpa_consent` เก็บเป็น JSON ที่มีรายละเอียดมากกว่า
→ [[CRM - Data Dictionary]] · [[Consent & PDPA]]

**ต้องยืนยันก่อน:** JSON ใน `members.pdpa_consent` มี timestamp กับ channel จริงหรือไม่ ถ้าไม่มี ทั้งกลุ่มก็ยังไม่มีใครตอบได้

## ฟิลด์ที่ไม่มีเลย (25 ตัว) — แยกตามสาเหตุ

### 1. ไม่มีเพราะอยู่ระบบอื่น — ไม่ต้องแก้ที่ K2 (14 ตัว)

| BU | ฟิลด์ | ควรมาจาก |
|---|---|---|
| ค้าปลีก | ช่องทางการซื้อ (หน้าร้าน/ออนไลน์) · ความถี่ในการซื้อซ้ำ | ITEC |
| บริการ | ประวัติเข้ารับบริการซ่อม | iCare |
| ประกัน | เลขกรมธรรม์ · ประเภทประกัน · วันเริ่ม/ครบกำหนด · ประวัติการเคลม | iCare Insurance |
| EV | รุ่นรถที่สนใจ/ซื้อ · ประวัติ Test Drive · ข้อมูลสินเชื่อรถ | GIcore / EV Core |
| สมาชิก | Loyalty / Membership ID | CRM (`members.member_id`) |
| KYC | KYC Status · KYC Date | ยังไม่ทราบเจ้าของ |
| การชำระ | ช่องทางการชำระ | มีใน K2 (`PAYMENT`) แต่ไม่ได้ระบุในสำรวจนี้ |

> **Loyalty ID ปิดได้แล้ว** — CRM มี `members.member_id` (รูปแบบ `M06xxxxxxx`) และเชื่อม ITEC ผ่าน `itec_cuscode`
> **KYC ยังเป็นคำถามเปิด** — ยังไม่รู้ว่าระบบไหนถือข้อมูลนี้

### 2. ขาดจริงในฝั่งข้อมูลตัวตน (7 ตัว)

| ฟิลด์ | ผลกระทบ |
|---|---|
| ชื่อกลาง ไทย / อังกฤษ | ต่ำ — ชื่อไทยแทบไม่มีชื่อกลาง |
| ชื่อกิจการ (นิติบุคคล) · วันจดทะเบียนบริษัท | **สูงถ้าจะทำ B2B** — โครงสร้าง K2 เป็น personal-only |
| ที่อยู่ปัจจุบัน (ถ้าต่างจากบัตร) | **สูง** — กระทบการส่งหนังสือบอกเลิกสัญญาโดยตรง ⚠️ |
| เบอร์โทรสำรอง | กลาง — กระทบงานติดตามหนี้ |
| สถานะวีซ่า / Work Permit | ต่ำ — เว้นแต่จะปล่อยสินเชื่อชาวต่างชาติ |

> **"ที่อยู่ปัจจุบัน" ต้องตรวจซ้ำ** — ตาราง `ADDRESS` ของ K2 มีที่อยู่ **5 บล็อก** และชุด collection ที่ส่งจริงมี
> `CUSTOMER_ADDRESS_REGISTER` / `CUSTOMER_ADDRESS_CURRENT` / `CUSTOMER_ADDRESS_DELIVERY` แยกกันอยู่แล้ว
> → ข้อนี้อาจเป็น **1 ไม่ใช่ 3** ต้องยืนยันกับผู้กรอกแบบสำรวจ ดู [[K2 - Customer & Address]]

### 3. ต้องคำนวณเอง ไม่ใช่ฟิลด์ (2 ตัว)

| ฟิลด์ | ทำได้ไหม |
|---|---|
| เงินคงเหลือสุทธิ | **คำนวณได้** = รายได้ − ภาระผ่อนรวม (มีทั้งสองตัว) |
| Debt Service Ratio (DSR) | **คำนวณได้** = ภาระผ่อนรวม ÷ รายได้ |

ทั้งสองเป็น **derived metric** ควรสร้างที่ชั้น Silver/Gold ไม่ใช่ขอจากต้นทาง
→ [[ETL & Spark]]

### 4. ผู้ติดต่ออ้างอิง (2 ตัว)

ชื่อกลางผู้ติดต่ออ้างอิง · ช่องทางติดต่อสะดวกอื่นๆ — ผลกระทบต่ำ
