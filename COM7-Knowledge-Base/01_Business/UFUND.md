## กติกาธุรกิจที่ต้องรู้

| เรื่อง                             | กติกา                                                                                      |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| **วันครบกำหนดชำระ**                | K2 = วันที่ **1** และ **16** เท่านั้น · ITOS = หลากหลาย (14, 20–23, 26, 27)                |
| **การนับ OD**                      | นับงวดที่ยังไม่มีใบเสร็จและเลยกำหนดแล้ว — OD1 ถึง OD6                                      |
| **ระบบ refresh สถานะ OD**          | วันที่ **3** และ **18** (ช้าจากวันครบกำหนดประมาณ 2 วัน)                                    |
| **สถานะสัญญาเป็น sticky**          | ขึ้น `48 = Overdue 6` แล้วไม่ลดลงแม้จ่ายบางส่วน — ต้องดู `NUMBER_OF_OD_INSTALLMENT` ประกอบ |
| **เกณฑ์บอกเลิกสัญญา**              | ค้างชำระครบ **6 งวด** หรือสัญญาหมดอายุแล้วยังค้างครบ 6 เดือน                               |
| **ค่าเบี้ยปรับล่าช้า / ค่าติดตาม** | มีตารางอัตราตามยอดหนี้และงวดที่ค้าง → [[K2 - Fee Policy]]                                  |

กติกาฉบับเต็มพร้อมหลักฐาน → [[K2 - Business Rules]]

### "เลี้ยง OD" คืออะไร

ลูกค้าที่จ่ายพอไม่ให้ถูกยึดของ แต่ไม่เคยตามงวดทัน — จ่าย 1 งวดเมื่อค้าง 6 งวด แล้วค้างต่อ
ผลคือสถานะยังเป็น 48 แต่ตัวนับงวดค้างขึ้นๆ ลงๆ อยู่ระหว่าง 4–6 ตลอด
พบว่าเป็น **สัดส่วนใหญ่ของพอร์ต OD6** → [[OD6 Collection Delivery]]

## ข้อจำกัดที่ค้นพบ

| ข้อจำกัด | ผลกระทบ |
|---|---|
| **ไม่รองรับลูกค้านิติบุคคล** | ไม่มีชื่อกิจการ/วันจดทะเบียน — ทำ B2B ไม่ได้ในโครงสร้างปัจจุบัน |
| **PDPA ไม่ครบ** | ทั้ง 4 ฟิลด์ compliance ต้องทดแทน ไม่มีตรงๆ สักตัว |
| **FK แค่ 16 จาก 542 ตาราง** | ความสัมพันธ์ต้องอนุมานและทดสอบเอง |
| **ตารางขยะเยอะ** | `_BACKUP` `_TEMP` `_TEST` ลงท้ายวันที่ — `CUSTOMER_CARD` มีฝาแฝด 8 ตัว |
| **`COLLECTION_OD` ไม่มี index เลย** | query ช้ามาก (104 วิ vs 4.5 วิ) — กระทบวิธีเขียน SQL |
| **[ต้องยืนยัน] K2 อาจมีข้อมูล EV ปนอยู่** | เอกสารเทียบระบบ EV ระบุว่า K2 ทำใบแจ้งหนี้/บิลค้างให้ EV ด้วย → [[EV China Benchmark]] |
